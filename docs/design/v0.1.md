# Netweir v0.1 design

Status: draft, October 2026
Author: James Conway

## What v0.1 is

Netweir is a web scraping library with a Rust engine and a Python API. Version 0.1 covers three things: fetching pages so they look like they came from a real browser, parsing them fast, and crawling whole sites without losing work when something breaks.

A browser driver, a stealth layer for JavaScript-heavy sites and a hosted service all come later. v0.1 leaves room for each of them but builds none of them.

The goal for v0.1 is to be the fastest Python crawler you can install, measured in public, in CI, against Scrapy, Scrapling and a hand-rolled httpx + selectolax script.

## Scope

In v0.1:

- HTTP/1.1 and HTTP/2 fetching with Chrome, Firefox and Safari TLS and HTTP/2 fingerprints
- An HTML parser with CSS selectors, XPath 1.0 and a Beautiful Soup style `find` / `find_all`
- A crawl engine: priority queue, per-domain concurrency, dedup, robots.txt, adaptive throttling
- Declarative spiders that run with no Python per page, and ordinary spiders with an async `parse`
- Self-healing: tracked selectors that survive markup changes, block detection and recovery, crash-safe resume, and an optional LLM selector repair plugin
- Exporters for JSONL, CSV and Parquet
- A `netweir` command line tool
- Wheels for macOS, Linux and Windows on arm64 and x86_64, Python 3.10 and up, plus free-threaded 3.14t

Not in v0.1:

- HTTP/3. No Rust stack can copy a browser's QUIC fingerprint yet.
- A browser driver. Planned for v0.2, over CDP.
- Multi-process workers. The engine is designed for them; they ship in v0.2.
- Fingerprint rotation services, residential proxies and CAPTCHA handling. These belong to the hosted service and never go in this repo.
- Login automation.
- Requests a browser makes on its own around a navigation, such as `/favicon.ico` after each page. That belongs with the browser driver.
- Drop-in compatibility with Scrapy or Beautiful Soup. The concepts carry over; the API is new.

## Architecture

Python runs the crawl loop. Rust does the work.

```
Python (user API)                         Rust engine (one per crawl, own tokio runtime)
─────────────────                         ────────────────────────────────────────────
Spider class / declarative rules  ──────► Frontier: priority queue, per-domain slots,
async for batch in engine.results():       dedup (fingerprint), robots.txt + TDMRep,
   custom callbacks (if any)                adaptive per-domain delay
   yield items / requests  ─────────────►  Fetcher (wreq): profiles, cookies, proxies   
Pipelines / exporters (Python or           Block classifier → retry / rotate / back off
   built-in Rust: JSONL, CSV, Parquet)     Parser + CSS + XPath (rayon pool)
                                           Declarative extractor (no Python)
                                           Checkpoint store (SQLite, WAL)
```

The reasoning: on a single site, crawl speed is set by the network and by politeness. Across many sites, it's set by CPU time per page, and most of that goes on parsing, on framework overhead and on running user code. Parsing and framework work move to Rust threads that never hold the GIL. User code only runs when the spider has a custom callback, and declarative spiders don't.

Python and Rust meet at one place, a bridge module in `netweir-py` built on pyo3-async-runtimes. Python asks for completed work in batches, so the event loop wakes once per batch, not once per request. If pyo3-async-runtimes turns out to be the bottleneck, the bridge is the only file that changes.

The crawl state on disk does not depend on Python, so a later version can run N Python worker processes against one engine for spiders with heavy custom callbacks.

### Sessions

A session is a browser profile, a proxy and a cookie jar, bound together. They are always swapped together, never one at a time. Most bot detection today catches requests whose layers disagree with each other (a Chrome TLS handshake with a Firefox user agent, a US proxy with a German `Accept-Language`), not any one signal on its own.

## Components

### netweir-dom

No Python and no network, so it can be tested and benchmarked alone.

- lexbor (Apache-2.0, C) parses the page and holds the tree. It is a git submodule pinned to a release tag, compiled by `build.rs` with the `cc` crate, so a build needs a C compiler and nothing else.
- Rust reaches lexbor only through a small C file of accessor functions, never through lexbor's struct layouts, which change between releases.
- lexbor's own selector engine runs CSS queries. `::text` and `::attr(name)` are stripped from the query before matching and applied to the result in Rust.
- XPath 1.0 is written from the W3C recommendation: every axis, the full function library, `$variables`, and the extensions Scrapy users rely on (`has-class()`, EXSLT `re:test()` and `re:replace()`). Results come back as Scrapy's parsel gives them (`3.0` for numbers, `1`/`0` for booleans). A query nested deeper than 256 levels (brackets, predicates, operator chains) is an `XPathError`, never a stack overflow, because LLM repair will feed generated XPath in. `re:replace()` reads its replacement as lxml does (`\1`, `\g<name>`).
- The first XPath query on a document builds a flat index of its nodes in document order: lexbor pointer, parent, end of subtree, type and tag id, with each node's number kept in lexbor's `user` field. A node's descendants are then a contiguous range, so `//x` is a scan over small arrays, children are found by jumping subtree ends, and document order is an array read. `//x[pred]` runs as one descendant scan grouped by parent rather than a child scan from every node, and `[@a = 'v']`, `['v' = @a]` and `[@a]` are answered from the element without building its attribute list. A step whose first predicate is `[k]` stops at the kth node on the axis, so `following-sibling::dd[1]` from every `<dt>` stays linear, and `id()` looks ids up in a table built on first use. Every fast path is tested against the long form it replaces, on nested markup.
- A `<template>`'s contents are its children, as in lxml and Beautiful Soup. lexbor parses them into a separate fragment; they are moved under the template when parsing ends.
- Elements, comments and text serialise as Chrome's `outerHTML` does: an attribute value containing `"` is written with `&quot;`, and an empty attribute as `name=""`. lxml (and so parsel) writes those differently; counts and order agree.
- encoding_rs and chardetng handle character encodings.

Python sees an `Arc<Document>` and small node handles (document reference plus node pointer). A query's results are entries, each a node or a string (an attribute value or a computed XPath value); indexing a selection gives a `Node` for elements and comments and a `str` for text and values. Bulk calls such as `.getall()` return `list[str]` straight from Rust without creating a Python object per node. Parsing, queries and serialisation release the GIL.

Why lexbor and not html5ever: measured on a 1.4 MB page, html5ever's tokenizer alone took 12.5 ms, while lexbor parsed the whole page in 4.2 ms. Copying lexbor's tree into a Rust arena cost another 2 ms, which lost to selectolax, so the tree stays in lexbor's memory. Running the query and building the strings in Rust is what puts Netweir ahead of selectolax, which uses the same parser.

Some inputs are slow for any HTML5 parser: thousands of unclosed `<div>`s make parsing quadratic in nesting depth (400 KB took 5 s in lexbor and longer in html5ever). Browsers cap the depth; lexbor doesn't. So parsing is chunked, and the crawler parses with a time budget and gives up on pages that blow it.

The parser follows the HTML5 spec, so it inserts `<tbody>` the way browsers do. Selectors copied from browser devtools work. Some written for lxml won't, and the docs say so.

### netweir-core

**Fetcher.** wreq, btls and http2, unmodified and pinned. Chrome 154's handshake (ML-DSA and GREASE signature algorithms, the trust_anchors extension) needs wreq and btls commits that are not on crates.io yet, so those two are pinned to exact git revisions through `[patch.crates-io]`, and netweir-core stays off crates.io until they are released; the Python package is unaffected. BoringSSL builds with CMake. wreq-util is not used: its licence has changed four times, including to GPL-3.0.

`Fetcher` is a concrete type. The trait a remote backend needs is extracted when a second backend exists, which touches one file. If the single maintainer of wreq stops, the first replacement is our own HTTP/2 layer on Cloudflare's `boring` crate.

**Profiles.** Browser profiles are Netweir's own data, in `profiles/*.toml`, compiled into the library. Each is written from captures that the `netweir-fingerprint` crate's `capture` tool records from the real browser, over HTTP/2 and HTTP/1.1, and the captures are committed beside it. A capture is four top-level navigations: a page that sets a cookie, a revisit, a cross-site redirect and a same-site redirect. The header list carries HTTP/1.1's capitalisation; HTTP/2 lowercases it and drops `Host` and `Connection`. An empty value holds a position for a header filled per request: `Cookie` comes from the jar, and over HTTP/2 each cookie is its own field, as Chrome sends them. After a redirect Chrome orders the same headers differently (client hints move after `Sec-Fetch-Dest`), so a profile can carry a `redirect_header_order`. Headers Chrome sends only over HTTP/2 (`priority`) are listed separately and added per request when the request will use HTTP/2. Firefox 156 is captured and tested the same way, driven through the four navigations with WebDriver; its profile adds what Firefox needs and Chrome doesn't: an exact extension order (Firefox neither shuffles nor GREASEs), `record_size_limit`, delegated-credential signature schemes, zlib and zstd certificate compression, and its TLS 1.3 cipher order kept as listed. Safari 27 is captured the same way, driven with safaridriver. Its profile adds two behaviours: `cookies_newest_first`, because Safari sends cookies of equal path length newest first, and `remembers_http1`, because once an origin has answered over HTTP/1.1 Safari offers new connections to it only `http/1.1`. Safari keeps a connection opened before it learned that, and may send later requests on either; the HTTP/1.1 test accepts either connection's ALPN offer for a request Safari sent on a connection opened before the navigations began. The fingerprint test compares extension order for browsers that don't shuffle. `profile="chrome"`, `profile="firefox"` and `profile="safari"` mean the newest of each.

**Redirects.** `Fetcher` follows redirects itself, one request per hop, up to Chrome's limit of 20, so each hop gets fresh cookies from the jar, the after-redirect header order, and HTTP/2-only headers decided for that hop's origin. `Sec-Fetch-Site` stays `none` through a navigation's redirects, as in Chrome.

**HTTP/2 support by origin.** Netweir remembers which https origins (`host:port`) answered over HTTP/1.1 and sends them no HTTP/2-only headers. The first request to such an origin can't know, so it carries `priority`; the fix belongs in wreq: a hook that drops marked headers once a connection turns out to be HTTP/1.1.

**Fingerprint test.** `netweir-fingerprint` also runs a local HTTPS server that records every request on every connection: ClientHello, JA4, HTTP/2 frames and headers in order. It sets cookies and redirects on request (`?set=`, `/redirect?to=`). netweir-core's tests replay the captured navigations against it and fail on any difference from the committed capture, ignoring only what the browser itself randomises (GREASE values, extension order, session resumption) and the test server's own host and port.

Thin PyO3 bindings and the async bridge. No logic lives here that could live in core.

## Python API

### One-off fetch and parse

```python
import netweir as nw

page = nw.get("https://books.toscrape.com/", profile="chrome")

page.css("h1::text").get()  # "All products"
page.css(".price_color::text").getall()  # ["£51.77", "£53.74", ...]
page.xpath("//article//h3/a/@title").getall()
page.find("li", class_="next")  # Beautiful Soup style, same node type
page.status, page.headers, page.blocked  # blocked: None | "cloudflare" | "datadome" ...

async with nw.Client(profile="firefox", proxy="http://...") as client:
    pages = await client.get_many(urls)
```

A page is a response and a parsed document in one object. `css`, `xpath` and `find` return the same node type, so they can be mixed. `nw.get` is the only synchronous entry point; everything else is async.

`get()` on an element gives its HTML, as parsel does; `::text` and `::attr()` give strings. Each selector in a comma list keeps its own ending, and results merge in document order. A selection also has parsel's `re()`, `re_first()`, `attrib`, slicing, and `extract()`/`extract_first()`. `re()` runs Python's own `re`, so every flag and Python's syntax work, with parsel's `extract` group and entity decoding.

The Beautiful Soup style API lives on `Node`: `find`, `find_all` and the directional families (`find_parent(s)`, `find_next_sibling(s)`, `find_previous_sibling(s)`, `find_next`/`find_all_next`, `find_previous`/`find_all_previous`), with filters that are a string, a list of strings and compiled regexes, True/False, a compiled regex or a function, plus `class_`, `string=` (or the older `text=`), `limit` and `recursive`. An attribute filtered with `None` must be absent, and `class`, `rel`, `rev`, `headers`, `accept-charset`, `accesskey` and `dropzone` match any one of their values. Navigation (`parent`, `children`, `contents`, `descendants`, siblings, `next_element`/`previous_element`), `get_text`, `.string`, `node["href"]`, `node.get()`, `select`/`select_one` match Beautiful Soup. Like Beautiful Soup 4.10 and later, `.text` and `get_text()` leave out the contents of `<script>`, `<style>` and `<template>`. Attribute values are strings, not Beautiful Soup's lists for `class` and `rel`.

### Declarative spider

```python
class Book(nw.Item):
    title = nw.css("h1::text")
    price = nw.css(".price_color::text", re=r"[\d.]+", into=float)
    upc = nw.xpath("//th[.='UPC']/following-sibling::td/text()")


class Books(nw.Spider):
    start_urls = ["https://books.toscrape.com/"]
    rules = [
        nw.Follow("li.next a"),
        nw.Follow("article.product_pod h3 a", extract=Book),
    ]
```

```
$ netweir crawl books.py -o books.jsonl
```

No Python runs per page. Python only sees finished items.

A field is `nw.css(query)` or `nw.xpath(query)` with `re=` (Rust regex syntax; the first group if the pattern has one, else the whole match), `all=True` for every result instead of the first, `strip=True`, `default=` for nothing found, and `into=`. `int`, `float`, `bool` and `str` convert in Rust; a value that won't convert is stored as None and warned about once per field with its text. Any other callable runs in Python on the finished item, so it costs Python time per item, not per page. Fields compile when the class is defined, so a bad query or pattern fails there. `Item.extract(page)` runs the same extractor inside an ordinary callback.

`nw.Follow(css | xpath=, extract=, callback=, follow=, priority=)` takes each matched element's `href`, or the strings a query ending in `::attr()` or `@href` gives, resolved against the page's `<base href>` and then its URL. As in Scrapy, `follow` defaults to True for a rule with neither `extract` nor `callback` and False otherwise. Start pages, and requests yielded without a callback, have the rules applied; `parse` runs on them as well only if the spider defines it. A rule with a `callback` hands its pages to Python with the tree the engine already parsed.

The rules leave alone a page with an error status or a body that isn't HTML (logged at info, counted as `pages_ignored`), since a 404 page is no product. A query that fails on a page, such as an XPath type error, is reported as a failed query, not a bad value; warnings name the field as `module.Class.field`, once per crawl. With `all=True`, nothing found is an empty list and `default` is not used. Links are deduplicated per page before they are queued. How it runs: every request carries a tag saying whether to apply the rules, which item to extract, and whether Python wants the page. When the engine's next batch contains tagged pages, each is parsed and processed on a blocking thread, at most one per core at a time, under a 10-second parse budget (a page that runs over is not handed to Python either, which would parse it again without one); links are queued directly, and only items, and pages with a Python callback, reach Python. Requests the rules make take ids from 2^62 up, so they never collide with Python's.

### Spider with a callback

```python
class Quotes(nw.Spider):
    start_urls = ["https://quotes.toscrape.com/"]

    async def parse(self, page):
        for q in page.css("div.quote"):
            yield {
                "text": q.css(".text::text").get(),
                "author": q.css(".author::text").get(),
                "tags": q.css(".tag::text").getall(),
            }
        if nxt := page.css("li.next a::attr(href)").get():
            yield page.follow(nxt)
```

`rules` and `parse` can be combined: rules handle link following in Rust, and `parse` runs only on the pages that need it.

### Tracked selectors

```python
price = page.css(".price_color", track="price")
price.relocated  # True if the original selector missed and the element was found by similarity
price.score  # similarity of the match, 0 to 1
```

`track=` also works on `nw.css(...)` and `nw.xpath(...)` fields.

When a tracked selector matches, Netweir stores a fingerprint of the element: tag, text, class, id and attribute names, the tag path of its ancestors, its siblings' tags, its parent's tag and class, and the nearest text before it (often a label). Fingerprints are keyed by site and track name and stored in the checkpoint file, or in `~/.netweir/tracks.db` (`$NETWEIR_HOME/tracks.db`) otherwise, and written only when they change.

When the selector later finds nothing, every element of the same tag family (h1 to h6 are one) is scored against the fingerprint: text 0.45 (a changed price keeps its shape), attributes 0.15, preceding text 0.15, ancestry 0.10, parent 0.10, siblings 0.05, with evidence present on one side only counting as neutral. The weights are tuned on hand-made before-and-after pairs in `crates/netweir-dom/tests/fixtures/redesigns/`. The best match is returned if its score clears `Settings.track_threshold` (default 0.75), and the query's ending (`::text`, `::attr()`, `/text()`, `/@x`) is applied to it. Below that, the result is empty and `score` is the nearest candidate's. A warning is logged once per site and name, and the stats count `relocated` and `lost`. A tracked query is one selector, not a list, that finds an element (with at most an ending), and XPath tracking doesn't take `$variables`.

Three rules keep relocation from inventing data. Each time a tracked selector matches, the new fingerprint learns from the old whether the element's text, and the text before it, change from page to page (a product's price and name do); varying text is compared by shape only, and a varying label counts as neutral, so relocation works across the pages of a crawl, not only on the page it learned from. A label that never varied and now reads differently rules a candidate out (the Shipping cell is not the Total cell). And when several elements still carry all the remembered element's classes, the selector missed one item of a list (a sold-out product's price), so nothing is relocated. Scoring reads at most the start of each element's text and its first siblings, so relocation on a page of 18,000 elements takes well under a second. Fingerprints from `page.css(track=)` and rules are keyed by the page's host; `track=` on a bare Node (`netweir.parse`) uses an empty site.

The optional `nw.repair.llm(model=..., complete=..., report=...)` plugin takes a broken tracked selector (relocated or lost) and the page, and asks a model for a replacement. `complete` is any prompt-to-text function; the default uses Anthropic's API. Each proposal is checked on the page (does it parse, what does it find, how similar is that to the fingerprint), logged, kept on `spider.repairs` and appended to the `report` JSON Lines file. It never applies a fix on its own. Repairs are asked once per site and name, after the crawl, off the event loop. What is sent: the page's HTML without scripts, styles and comments (up to 40,000 characters), its URL, the old selector and the fingerprint; a custom `complete` can redact or use a local model. The Anthropic request times out after two minutes.

### Settings, pipelines and output

```python
class Books(nw.Spider):
    settings = nw.Settings(
        concurrency=256,
        per_domain=8,
        profile="chrome",
        obey_robots=True,
        checkpoint="crawls/books",
    )
    pipelines = [drop_out_of_stock, nw.export.jsonl("books.jsonl")]


async def drop_out_of_stock(item):
    return item if "In stock" in item["stock"] else None
```

A pipeline is a function, sync or async, that returns the item, a changed item, or `None` to drop it. The built-in exporters run in Rust and are chosen by extension when `run(output=...)` or `-o` names a file:

- **JSON Lines** (`.jsonl`, `.jl`): one object per line, keys in the item's order. Dates become ISO 8601 strings, `Decimal` and integers beyond 64 bits become strings, NaN and infinities become null.
- **CSV** (`.csv`): columns are `fields=` if given, otherwise the first item's keys. Keys outside them are left out with one warning each; nested values are written as JSON.
- **Parquet** (`.parquet`): column types (bool, 64-bit integer, double or text) come from the first 1,000 items. A key that holds both integers and floats is a double column, any other mix is text, and lists and dicts are stored as JSON text. Later values that don't fit their column are stored as null, later keys with no column are left out, and closing the file logs a warning for each. Row groups hold 10,000 rows; compression is Snappy.

`netweir crawl FILE -o OUT -s KEY=VALUE` runs a spider from the command line, `--spider NAME` picks one when the file defines several, and an unknown setting exits with status 2. An exception in a callback or pipeline is logged with the request's URL and counted in the stats; `Settings(fail_fast=True)` stops the crawl on it instead.

**Crawl engine.** Requests wait in per-host priority queues, under a limit on requests in flight overall (`concurrency`, 64) and per host (`per_domain`, 8). Before a host's first page, its robots.txt (RFC 9309) and `/.well-known/tdmrep.json` are fetched once; requests to that host wait for both. A page's own `tdm-reservation` header, then its meta tag, override the site's file. Each host's delay starts at `start_delay` and moves halfway toward the response latency divided by `target_concurrency` after every response; a 429 doubles it, only a 200 can shorten it, and a robots.txt `Crawl-delay` is a floor. The engine follows redirects itself, one hop at a time (`Fetcher::hop`): each target is queued on its own host, so it passes that host's robots.txt, TDMRep and limits, and counts as seen. robots.txt and tdmrep.json fetches count against `concurrency`. When twice `concurrency` results are waiting for the reader, no new fetch starts, so a slow callback doesn't mean the site downloaded into memory. The scheduler visits only hosts that may be able to start something, keeping hosts that wait out a delay in a timer heap. robots.txt, TDMRep and page fetches run in a guard that turns a panic into a safe outcome (disallow everything, no file, a failed request), so the crawl's bookkeeping always happens. A request is a duplicate if the SHA-256 of its method and canonical URL (lowercased scheme and host, no default port or fragment, tracking parameters such as `utm_*`, `fbclid` and `gclid` removed, query sorted) has been seen. Results reach Python in batches of events, so the boundary is crossed once per batch, not per page.

### Defaults

Netweir obeys robots.txt and TDMRep, and throttles per domain, out of the box. The default user agent is the profile's real browser user agent. Turning robots.txt off is an explicit setting (`obey_robots=False`) that logs a warning once per crawl. HTTP 402 is always surfaced, never retried.

## Errors and recovery

### Outcomes

Rust classifies every fetch into one outcome before Python sees it.

| Outcome | Example | Default handling |
|---|---|---|
| `ok` | 200 with content | parse, extract, follow |
| `blocked(vendor, kind)` | `cf-mitigated: challenge`, DataDome 403, Kasada 429, AWS WAF 202 | new session, retry |
| `throttled` | 429 or 503 with `Retry-After` | wait, slow the domain |
| `payment_required` | 402 with a price header | never retried, reported with the price |
| `http_error(status)` | 404, 500 | 5xx retried with backoff, 4xx recorded |
| `network_error(kind)` | timeout, DNS, TLS, reset | retried with backoff |

In a crawl these are data: they show up in stats and the `on_block(request, page)` hook, which logs by default and may yield items or Requests like a callback. `page.outcome` and `page.blocked` (the vendor) expose the classification. `nw.get` and `Client.get` raise `nw.Blocked` on a block unless called with `raise_on_block=False`. A 429, or a 503 with Retry-After, is `throttled`; Retry-After is read as seconds or as an HTTP date. A 402's price is its `crawler-price` header.

### Block classifier

Checks run in order of reliability: headers, then cookies, then body markers, then status code. Vendor signatures (Cloudflare, Akamai, DataDome, HUMAN, Kasada, Imperva, AWS WAF) live in `signatures/blocks.toml`, compiled into the library, so adding a signature is a data change. A body marker always comes with a status, a header or a cookie, so a page that merely mentions a vendor isn't a block, and markers are chosen from block pages only: Imperva, for one, sets its cookies and injects its script on every page it serves, so only its challenge iframe and incident text count. Header values match ignoring case. Each vendor has a fixture in `crates/netweir-core/tests/fixtures/blocks`, written from the vendor's documentation and published examples rather than recorded from live traffic (the tests never contact vendors), next to pages that must not count as blocks.

### Recovery ladder

Per request, each step only if the last failed:

1. Retry on the same session after a random wait of up to `backoff_base` × 2^n, capped at `backoff_max` (full jitter): 408, 500, 502, 503, 504, 522, 524 and transient network errors. Other 4xx and 402 are never retried.
2. New session: a fresh cookie jar, and the next of `Settings.proxies` when there are several (blocks), only when a retry will use it. While Chrome is the only profile, the profile stays.
3. Slow the domain: blocks and 429s double the host's delay (to at least 0.5 s), once, from now rather than from its next turn, and Retry-After pushes it back further. With the throttle off, good responses halve the delay again.
4. Circuit breaker: if more than `breaker_ratio` (30%) of the host's last `breaker_window` (50) responses were blocks, the host pauses for `breaker_pause` (5 minutes) and one warning is logged. It judges once it has seen 10 responses (or the window, if smaller), so a site that blocks from the start pauses quickly.
5. Give up after `retries` (3) further tries: a block reaches `on_block`; other failures reach the errback or the log.

Every step is a setting and a stats counter (`retries`, `blocked`, `throttled`, `sessions_replaced`, `breaker_trips`). In v0.2, a step between 4 and 5 escalates to a real browser.

### Crash safety

`Settings(checkpoint="crawls/books")` keeps the crawl in `crawls/books/crawl.sqlite3`: SQLite in WAL mode, written by one thread that commits queued writes in order, a batch at a time, so after a crash the file holds everything up to some point and nothing after it. Requests are stored as plain data with callbacks referenced by name (so with a checkpoint, a callback must be a spider method and `meta` must be JSON). Nothing is pickled.

After `kill -9`, rerunning the same command resumes the crawl: unfinished requests are queued again and seen fingerprints restored. A request is marked done only after Python has finished with its batch, so delivery is at least once: requests in flight at the crash are fetched again. Every item from a crawl with a checkpoint carries a stable `_id` (a hash of the page's fingerprint and the item's position in that page's output), and items already delivered are skipped. Before items are recorded as delivered, JSONL and CSV outputs are flushed to disk, and the item ids and each file's length are committed together; a resumed run cuts each file back to its recorded length (dropping a half-written line) and appends, so every item appears once. Parquet is readable only once closed: each part is written under a `.partial` name and renamed only after its items are on record, a resume finishes a rename that was recorded but not done and deletes any other `.partial`, and a resumed run writes the next part (`books.1.parquet`). A crawl that can't start (a checkpoint from a newer Netweir, say) leaves its output files untouched. A failed checkpoint write is reported by the next flush. Dict items carry `_id` as a key; dataclass items are deduplicated by it without showing it. The crash test kills a crawl at random moments until it finishes and checks every item is present once.

The file records a format version. A newer Netweir resumes a checkpoint written by an older one, and an older Netweir refuses a newer file rather than misread it.

### Traps

Canonical URLs before dedup, `max_depth` (depth is carried on every request: start requests 0, followed links one more, redirects unchanged), `max_pages_per_domain`, and rejection of URLs whose path repeats a run of two or more segments three times in a row, or one segment four times (one segment three times, as in `/01/01/01/story` or `/1/1/1/photo.jpg`, is too common a real shape to refuse). Each is a submit result and a stats counter.

### User code

An exception in a callback or pipeline is logged with the page URL, counted, and the crawl continues. `fail_fast=True` stops on the first one.

## Room for the hosted service

v0.1 doesn't build the hosted service, but a few choices now keep it a plug-in later:

- All fetching goes through `Fetcher`, so a remote backend replaces one type.
- Request options use the same field names as the common hosted scraping APIs where they overlap (`httpResponseBody`, `geolocation`, `session`), and the request fingerprint includes them, since the same URL fetched two ways is two requests.
- Every response carries a `usage` field the hosted service can fill in for billing.
- Extraction is a separate step from fetching, so it can be priced separately.
- Items, logs and stats leave through one output interface a hosted collector can capture.
- A crawl reports its peak memory.

JA4 (BSD-3) is the only fingerprint the hosted service will compute. JA4H, JA4S, JA4T and JA4X are under the FoxIO License and need a paid licence for commercial use; their code stays out of this repo.

## Testing

**Rust.** `cargo test` on every crate. XPath tests are written from the examples in the XPath 1.0 spec. `cargo-fuzz` targets the parse and query entry points and the XPath parser. Hostile inputs (deep nesting, NUL bytes, random bytes) are in the ordinary test suite.

**Python.** pytest against `maturin develop --uv`.

**No live internet in gating tests.** A local test server stands in for the web: paginated sites, traps, slow and failing pages, and recorded block pages from each vendor.

**Fingerprints.** The test server records the TLS ClientHello and HTTP/2 frames of each request, computes JA4 and the Akamai HTTP/2 string, and compares them with the reference captured from the real browser. A profile that drifts by one extension fails CI.

**Crash recovery.** A crawl against the local server is killed with `kill -9` at random points and resumed. The test asserts no request was lost and every `_id` is unique.

**Live smoke tests.** Nightly, never gating: books.toscrape.com, quotes.toscrape.com and a TLS fingerprint echo service.

**Profile freshness.** A weekly job opens an issue when a new stable Chrome, Firefox or Safari ships.

## Benchmarks

| Benchmark | Compared with | Measure |
|---|---|---|
| Parse + query, 1 MB and 10 MB pages | lxml, selectolax, Beautiful Soup, parsel | ms per page. CI fails if selectolax is more than 5% faster |
| Crawl, 10,000 pages across 100 domains at 50 ms simulated latency | Scrapy, Scrapling's spider, an httpx + selectolax script | pages/sec, CPU-seconds per page, peak RSS |
| Declarative spider vs the same spider with `parse` | itself | what the Rust-only path saves |

Benchmarks run in CI. A pull request fails if it's more than 10% slower than a baseline run in the same job. Results are published in the README.

## Risks

| Risk | What we do |
|---|---|
| wreq has one maintainer, and Chrome 154 needs unreleased commits | Pinned to exact revisions; all fetching goes through one type. Replacement path: own HTTP/2 on `boring`. |
| The lead over selectolax is small (2–7%) because both use lexbor | The benchmark gates CI. The lead comes from batching in Rust, so it grows with the work done per page. |
| Hostile pages that are slow to parse | Chunked parsing with a time budget. |
| Browser profiles go stale every Chrome release | Captured by our own tool, checked weekly. |
| BoringSSL builds on Windows and musl | Native MSVC runners, not cross-compiling. Build times measured in the first CI run. |
| Tracked selector weights are guesswork | Tuned against a corpus of real redesigns, score exposed to the user. |
| Free-threaded Python and pyo3-async-runtimes | 3.14t in the test matrix from day one. |
